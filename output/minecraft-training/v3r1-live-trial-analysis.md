# v3r1 epoch-02 live trial: trajectory candidates

This is a read-only analysis of the live loop started at `2026-10-12T20:09:20.955Z` with the v3r1 epoch-02 adapter. The 19 matched decisions and terminal results are preserved in `data/minecraft-training/live-trial-v3r1-20261012-candidates.json`. These are real development candidates only; they are not training labels and were not merged into any frozen dataset. No holdout data was read.

The file reconstructs each planner message from the exact observation stored with `model_decision`, the loop goal, and the prior `model_action_result` history. The loop-start artifact confirms the initial history was empty. The original HTTP request bodies were not logged, so the message arrays are faithful reconstructions, not byte-for-byte captures of the requests.

The sequence includes 19 matched decisions: 13 executor `completed` results and six `failed` results. Two completed results were partial (`gather_wood 4` yielded one log and `gather_wood 6` yielded three). The initial `gather_wood 4` was a reasonable response to visible wood but made no progress because all candidate logs were above the safe height limit; the executor rejected unsafe tower-building. The later wood collection reached safe candidates, with partial gains and path/pickup verification failures recorded. These are executor/world outcomes, not proof that the planner chose an invalid action.

Material recovery was mixed. After gathering one log, the model crafted four planks and four sticks. It then tried to craft a table with only two planks, failed, tried crafting planks twice with no logs, and retried the table with the same shortage. After gathering four more logs, it crafted planks three times for twelve outputs, then sticks, a crafting table, and a wooden pickaxe. This shows useful recovery and successful progression alongside repeated impossible crafting and likely excess plank production. After the pickaxe, another planks craft consumed the remaining log but ended with `crafted batch inventory: server verification failed`; the output/result is uncertain, so this is retained as an executor-verification failure rather than a model-quality label.
