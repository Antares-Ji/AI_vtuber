# 持续语音通话独立验收

## 本轮交付与实测步骤

### 音量适应与耗时迭代

当前默认值更新：讲话持续 120ms 后确认起点，静音 550ms 分句。会话内保留正常音量估计，触发门槛取最低音量、背景噪声倍数、正常音量的 28% 三者的最大值；正常音量项设上限，避免一次喊叫把阈值永久抬高。不保存声纹、不识别说话人，每次新通话重新学习。页面的 dBFS 是数字音频电平，不是物理声压分贝。

先正常说两三句话，再测试短敲击、较小背景音不应打断，正常发言和适当轻声仍能打断。自动测试覆盖 20ms 冲击不触发、120ms 发言触发、跨轮学习保留、低音量背景过滤。

简单本地通话生成上限为 96 tokens、提示简短回答；详细/故事请求与复杂云端路径保持原预算。100 字以内已审核回复一次提交 TTS，避免短回复拆成两次请求。仍先审核后播出，不把未审核草稿当成记忆。

耗时行分别显示分句静音、排队、ASR、模型首字/完整回复、TTS 首音以及分句后到首音；等待用户真实通话数据，不承诺固定提速比例。一次短句合成回灌样本：ASR 124ms，模型首字 238ms / 完整 1436ms，TTS HTTP 头 1160ms（不是浏览器首音）。旧文下方 700ms / 单帧 onset 为历史默认值，以本节为准。

2026-09-06：新增“开始语音通话”，保留“语音发弹幕”。自动化测试不等于真实耳机验收；旧版用户实测打断 0/5，新版仍待用户实测。

1. 刷新直播页，选择麦克风、打开主播语音输出，戴耳机，点击“开始语音通话”。
2. 说一句话，停顿约 0.7 秒，等待回答。不需要再次点击录音。
3. 在回答播放中开口说“等一下，换个话题”，重复 10 次。目标：至少 9 次在半秒内停下，之后没有旧语音复活，并能回答新问题。
4. 连续交谈超过 2 分钟、至少 10 轮，麦克风不能被每轮关闭，无通话总时长倒计时。
5. 点击“结束语音通话”：立即关闭麦克风和播放，最后一段继续识别、保存后结束会话，不再生成回复。点击“查看本次通话记录”核对轮数和文本。

保存位置：`E:\Github\AI_vtuber\data\memory.db`，表 `voice_calls` / `voice_call_turns`。输入在等待模型前落盘，生成中取消保留 interrupted；completed 表示审核后的回复生成完毕，不代表用户听完所有音频。普通通话记录不是自动写入长期记忆的事实；长期记忆仍沿用明确“请记住”或审核候选的机制。录音本身不由此功能长期保存。

限制：目前是本地音量 VAD 加浏览器回声消除，不是说话人分离；外放回声、敲击声仍需实测。识别仍使用分句后的 ASR，不依赖未部署的原生流式模型。长句内部按 18 秒分块以限制内存，不结束通话；队列积压或识别失败会显示提示，不计作成功轮次。结束时会等待待识别片段完成（单次识别最长 30 秒）。

自动化：在项目目录执行 `npm run test:voice-call` 和 `npm run test:realtime`。

## 耳机打断 0/5 的历史根因审查（只读）

旧的弹幕双工路径仍以 `public/stream.js` 的 `startMicMeter()` 为 VAD 来源。以下条件任一成立，耳机打断就不会进入 `stopSpeechOutput()`：

1. 旧路径的 `AudioContext` 由 `startMicMeter()` 新建，但没有显式 `resume()`。浏览器自动播放策略或设备切换后若上下文处于 `suspended`，分析器读数可能长期为静音（`-Infinity`），因此 onset 永远不会成立。新 `VoiceCallController` 已在启动时显式 `resume()`。
2. 打断要求在 AI 仍被判定为 `aiSpeaking` 且输入连续高于 `-30 dB` 达 280 ms。任一动画帧低于阈值都会清零 `vadSpeechCandidateAt`；耳机麦克风的帧抖动、回声消除重收敛或蓝牙编码间隙足以让 280 ms 永远不连续。
3. `vadSpeechDetected` 一旦在 `aiSpeaking === false` 时被普通声音置为 `true`，随后 AI 开始说话时不会再进入 `!vadSpeechDetected && aiSpeaking` 分支；需要先静音分轮才能重新获得 onset 候选。
4. `startRecording()` 开头无条件调用 `stopSpeechOutput()`。如果用户是在 AI 播放后才按下持续通话按钮，AI 已被主动停止，随后不存在可被“耳机打断”的在途音源；这不是双工 onset 验收。
5. `aiSpeaking` 把 `activeReplyController`、TTS controller、已排队音源和 `activeAudio` 混为一个布尔值。回复控制器仍在但音源尚未开始时，输入阈值仍按 `-30 dB`；反过来上游结束但音源尚未清空时，状态窗口也可能错过。

因此“5 次 0 成功”不能只归因于阈值；必须先确认麦克风 `AudioContext.state === "running"`、VAD 帧有有限 dB 值，再判断 onset 连续窗口和 `aiSpeaking` 状态。

## 新持续通话行为级验收清单

新通话由 `VoiceCallController` 负责每轮语音，不把每轮当弹幕；默认静音收尾窗口为 700ms，`onsetFrames` 默认 1。每项都必须走生产 VAD → 回调 → 实际取消链，不能直接调用停止函数伪造成功。

- [ ] 会话开始后保持麦克风打开，无 90 秒倒计时；屏幕显示持续通话状态。
- [ ] 每轮静音达到 700ms 才结束该轮，不关闭会话；AI 播放期间由生产 onset 回调触发取消，旧音源实际调用 `source.stop()`，迟到 PCM 不创建新 source。
- [ ] 旧回复取消后启动新回复：旧回复的 catch/清理不能停止新回复音源。
- [ ] 点击“结束通话”立即停止麦克风与播放，待最后输入保存后释放会话；中途识别失败也必须可再次说话。
- [ ] 语音发弹幕仍是独立入口：最终转写文本进入 `/api/danmaku`，不与持续通话轮次混淆。
- [ ] 仪表板至少出现 `client_tts_first_pcm`、`client_tts_playback_end`、`client_barge_in_abort` 各 1 个样本；仅服务端 TTS 首字节不算通过。

## 建议的证据记录

每轮记录 `AudioContext.state`、输入 dB、`aiSpeaking`、`vadSpeechCandidateAt` 持续时间、`speechEpoch` 前后值、停止的 source 数量，以及会话是否仍 active。出现 0/5 时先保存这些字段，再调整阈值或重试。
