## 开发集比较与部署决定

v4r1 与 v6r1 使用同一进程、同一基座、同一冻结的 57 个开发输入作 greedy 直接推理；评估含原冻结 47 行和新独立 v6r1 开发 10 行。每个“可接受动作”统计都先要求严格 schema 有效，再对照精确动作或审核过的允许集合。本次 v6r1 选型未读取原 20 条验收样例；这 20 条在此前轮次已多次使用，不能称作全新未见 holdout。四个较早实机输入仅作无 gold 的诊断。

这组平均分提升不足以通过预先记录的“不能引入关键材料回退”标准。Astra 的独立复核确认了具体问题：在 `v4r1-dev-01` 中，背包有木镐、11 块木板和 8 根木棍、但没有圆石；v6r1 输出无法负担配方的 `stone_pickaxe`。在同一条实机诊断 `live-probe-1791836151666` 中，背包只有 1 根原木、没有木板；v6r1 仍输出需要 2 根原木的 `planks 8`。此外，新开发状态 food=20 且有牛肉时，v6r1 输出无效的 `eat`，而 v4r1 选择了采木。v6r1 也在已有石镐时重新制作木镐，虽材料可行，却没有推进工具阶段。

新开发集上也有局部收益：低饥饿进食、补采木材、批量制作木板、制作铁镐的样例有所改善；这不足以抵消上述关键回退。完整按行结果和 slice 统计见 [v6r1 开发集摘要](../output/minecraft-training/v6r1-development57-summary.json)，原始推理见 [v4r1](../output/minecraft-training/v6r1-dev57-v4r1.jsonl) 与 [v6r1](../output/minecraft-training/v6r1-dev57-v6r1-epoch01.jsonl)。独立判断见 [Astra 选型复核](../output/minecraft-training/independent-review/v6r1-selection-review.json)；最终冻结决定保留 v4r1 并拒绝 v6r1，见 [窗口选型记录](../output/minecraft-training/final-window-selection.json)。

直接推理的 v6r1 开发集延迟中位数约 1.77 秒；这不包括 Mineflayer 执行，也不是端点 metadata 或实机验证。四个诊断输入在两个适配器下均输出 schema 有效 JSON，但没有硬动作金标，尤其木材阶段输入材料不足以判定 `planks 4` 与 `gather_wood` 哪个策略必然更优。v6r1 没有进行实机部署或 live trial。

## 实机证据、归因边界与下一轮建议

先前 v3r1/v5r2 实机中出现过重复制作、材料不足后仍重试以及食物行为问题；部分失败来自执行层的可达性、库存核算或安全食物白名单，已由其它工作单独修补，不能计作模型学会了策略。v4r1 作为回退也没有通过自主生存或下界验收。现有对照说明微调数据质量、监督标签、开发集覆盖和执行器行为都会影响结果；这些证据不足以归咎于 4B 模型容量，也不能证明扩大训练量就能解决问题。

下一轮只建议准备数据与评估，不在本记录中启动训练或修改 prompt：

1. 继续以 v4r1 为回退；从新的 v4r1 实机窗口保存完整模型请求、动作、服务器结果和库存前后差异。把模型原动作、teacher 建议和执行结果分字段留存。
2. 做约 16–24 条成对材料与阶段反事实：同一配方分别“材料刚好够 / 少一件”，满饥饿与低饥饿配安全食物，已有高级工具与缺少工具，及工具/木材充足后向新阶段推进。每个动作都按 1.21.11 registry 配方、工具等级和实际观察到的资源审核；craftable 元数据必须与 runtime 一致。
3. 减少重复权重，避免每条新数据自动三次回放；用冻结且无归一化重叠的独立开发集检查材料可行性、food/no-op、工具升级和旧能力保留。先复核所有接受回归，再决定是否进行一次小幅续训。
4. 若之后获准训练，可从 v4r1 续训、rank 4、单 epoch，先考虑 LR `5e-6` 和新例最多 2 倍回放；保留完整 assistant 标签并冻结 dev 后再训练。训练 loss 不用于选型，v6r1 的结果表明低 loss 不能抵消不可执行的动作。

本轮没有使用 holdout 调参，没有部署 v6r1，也没有声称完成 Minecraft 生存或进入下界。
