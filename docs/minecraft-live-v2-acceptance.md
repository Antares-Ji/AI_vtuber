# Independent live v2 acceptance criteria

Fixed before the v2 live run, 2026-10-13. Frozen v1 holdout files and labels remain unchanged. The acceptance tool only reads logs and writes a report; it never starts inference or sends a game action.

Run with an explicit half-open UTC interval covering the actual v2 deployment and live trial:

```powershell
node scripts/minecraft-live-acceptance.js --autonomy logs/minecraft-autonomy.jsonl --session logs/minecraft-session-1791830191222.jsonl --from ACTUAL_V2_START_UTC --to ACTUAL_TRIAL_END_UTC --output output/minecraft-training/independent-review/live-v2-acceptance.json
```

Record the deployed adapter weight hash, training report, endpoint health, and implementation hashes at trial start. The tool records current checkout hashes at report time, which cannot by themselves establish what code was deployed earlier. Record reloads, operator interventions, task cancellation and service restarts in the trial narrative. Include every attempted model task in the chosen interval, including failures; do not select only successful segments.

## Measures and decision rules

- **Actual adapter use:** every model completion must supply `metadata.used_adapter=true` and the intended adapter path. Health-loaded status alone is insufficient. Missing or false metadata is a distinct cohort, never silently counted as v2. Pair the per-request metadata with a separately hashed adapter artifact.
- **Skill outcome:** report completed, failed, corroborated and partial outcomes separately. Inventory-producing actions require positive relevant item deltas; prefer the skill's own `inventoryBefore/After`. Outer observations can include changes during inference and are explicitly labeled weaker evidence. `verified:true` alone is insufficient. Exploration needs at least four blocks displacement; stairs need corresponding downward movement. Water/portal construction requires the executor's world verification fields. Entering the Nether requires an observed dimension transition. Observation and already-full eating are not progression. Positive partial harvest is progress but does not prove the requested quantity was met.
- **Repeated failure:** report immediate successive failures for the same action/item/resource/direction and same error category when position stays within two blocks and inventory is unchanged. Ignore count/distance and object key ordering. Divide repeated failures by all executed attempts, and report total failure rate separately. Unknown/missing comparison snapshots are not invented. Rejected plans are listed separately because no skill ran. Three unchanged failures are an explicit unresolved recovery issue, regardless of backoff speed.
- **Safety:** report all death events in the interval, threat-clearance and blocked-route events, and actual timing samples. Route issuance is not proof of successful escape: review subsequent displacement, threat separation and clearance before concluding recovery. If no threat episode occurred, label escape behavior untested. Any death needs its nearby threat/path/task context reviewed rather than attributing it automatically to the model.
- **Timing:** publish observed tick and sample-gap maxima; keep periodic sample values separate from cumulative maxima that can predate the selected interval. Report fallback overruns. Do not calculate per-tick percentiles from sparse periodic logs or claim that the 200 ms configured interval bounds response latency. Sustained sample gaps above one second during threat episodes are an investigation trigger, not an automatically established model failure.
- **Nether goal:** a recorded overworld-to-Nether transition is necessary but does not alone prove the user's requested survival route. Correlate model-selected tasks and actual inventory/world evidence for mining at least three diamonds, crafting a diamond pickaxe, cooling source lava with water into obsidian, mining enough obsidian for a standard portal (ten blocks when omitting corners), building and lighting it with crafted flint and steel, and entering it. An existing portal, donated materials, commands, or unrelated dimension changes do not prove this chain. Tools, iron, stairs, obsidian and a lit portal are intermediate achievements. No achieved stage is inferred from the action name alone.

## Attribution limits

Live v2 uses changes to weights, compact observations, recipes/failure context, execution skills, loop invalidation and reactive escape logic. Live improvement therefore measures the whole deployed system. It must not be called a pure LoRA gain. The frozen v1 benchmark remains an identical-input base-versus-adapter comparison with its fixed independent semantic rubric. A separate same-real-snapshot comparison can contrast weights only if messages, schema, generation settings and input are identical; preserve both requests and completion metadata. Do not use independent holdout labels for additional training or change existing holdout messages to the current planner prompt.

Before accepting the run, inspect the report's contradictory/missing evidence rows and malformed log lines. Zero logged deaths applies only to the provided session and time range. This audit corroborates recorded executor observations; it does not supply an independent game sensor or prove unattended reliability from a short trial.
