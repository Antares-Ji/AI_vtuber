# 导演控制台的原生视觉自动执行链

本次约束：游戏决策由角色 API 产生，画面事实由本地模型 API 读取，键鼠由项目原生 API 执行。开发助手负责启动任务、检查记录和修复程序，不代替角色选择卡牌、输入坐标或操作游戏。

## 入口与架构

```text
导演控制台 /studio.html#game-input
  → POST /api/skills/run（sts2:native-play）
  → Skill Host：任务、取消、预算、桌面资源互斥
  → 原生自主循环
      → /api/game-input/action：取得游戏客户端截图
      → /api/game-input/read-card → 本地 Qwen HTTP 服务
      → DeepSeek 角色决策 API：依据当前目标 ID 提议动作
      → 当前帧、能量、牌面、目标校验
      → /api/game-input/action：项目原生 Win32 键鼠
      → 下一帧重新观察，反馈上一步结果
```

统一 Skill Host 承接原有执行器。原 ZIP 的 Java 核心、Loader、Harness 和示例保持独立；本次没有改动其架构。原生视觉路径仅依赖共享的角色 API 设置，不再因读取配置而加载 STS2 MCP 客户端。MCP 模式仍保留自己的适配器和既有测试。

## 实测发现与修复

- 原始视觉会输出“手牌1”等泛称，角色曾据此推测牌名、费用和伤害。现在只有当前帧的完整牌名、费用、类型和描述通过校验后才允许拖牌；未知牌允许悬停，拒绝直接出牌，并把拒绝原因交给角色 API 重新规划。
- 战场和手牌分开读取。手牌裁剪坐标映射回原始客户端图像，不直接当作整图坐标使用。
- 悬停会把卡牌向上抬起。悬停后的手牌识别扩大纵向范围，并按悬停列裁剪读取完整牌面。同名、同费且位置匹配的唯一目标才能关联本帧牌面；有歧义时不关联。
- 展开牌可能被手牌列表漏掉。完整单牌 OCR 无法与列表对应时，再调用本地视觉目标定位 API；仅接受明确可见、位于原悬停列附近和展开高度范围内的本帧落点，然后交给角色 API 决策。
- 提示词中的示例文字可能被小模型照抄。读取提示改为字段说明；无效输出保留原始模型记录，不能转换为假坐标。
- 完全相同的目标事实和坐标可合为一个候选；同坐标但内容冲突仍失败。格式无效的分区识别最多重试一次，之后停止。
- 等待也进入角色历史，避免下一次决策不知道自己已经等过。停止一个已经结束的任务不再把最终状态改成“正在停止”。
- 角色请求包含按实际执行校验生成的可用动作摘要，明确哪些牌已经读清、可拖向哪些目标。摘要提供合法候选，最终选择仍来自角色 API。
- 奖励界面实测中，角色曾把视觉坐标字符串当作 targetId，输入被拒绝。规划上下文现在移除原始 points 和目标 point，仅保留具名 ID、标签和可用动作；坐标保留在执行层，未通过 ID 校验的操作不会发送。
- 本地视觉若只返回无标签坐标，不再静默转换为空目标列表。结构化场景读取要求实际标签，缺标签结果记录为无效观察；不能据此宣称界面没有可交互项。
- 清完奖励后，洞穴房间里的前进按钮曾被误归到路线地图。新增 room 场景，只有纸面路线、节点和连线网络才进入 map 专用定位；房间按钮仍由角色 API 按可见目标 ID 选择。
- 地图回退检查只统计实际点击，悬停不再触发自动提供返回按钮。连续八次地图／房间观察仍未进入其他场景时停止，防止变换目标、措辞或往返开关地图绕过原来的重复动作检查。
- 地图独立定位必须明确报告目标可见，且与地图观察器提供的候选处于同一邻域（归一化距离不超过 0.15）；两者明显冲突时停止，不用第二个坐标静默覆盖第一个。此阈值只是拒绝明显冲突，不能证明目标可达。返回和结束回合按钮也必须明确可见。
- 新增 `map-grounded` 本地视觉 API：OpenCV 从本帧像素提取红色标记和深色轮廓候选，程序自动裁剪、放大并标注编号，本地 Qwen 只返回当前位置标记 ID、直接相连节点 ID 和图标类型。位置始终来自像素候选，模型不能生成或覆盖坐标。原生循环逐项核对返回 ID 和像素坐标后，才交给角色 API 选择动作；不再对这条路径叠加原先容易指向当前位置的自由坐标定位。
- CV 不是路径规划器，候选不是可执行目标。红色标记不唯一、模型未确认、节点无明确直接连接、ID 不存在或目标不在当前位置上方时均拒绝。不同地图布局仍须继续实测。诊断模式 `map-cv` 仅返回像素候选，不产生游戏动作。
- 本地模型曾把按钮文字“结束第1回合”当成已经结束战斗。场景提示现明确区分按钮命令与结果；若 room 分类与本帧读到的完整结束回合按钮标签冲突，转入战斗分区观察，并保留原始模型输出及分类修正原因。不能仅依据“战斗结束”的摘要跳过实际可见控件。
- 战场整图摘要曾把能量分数或手牌里的“获得5点格挡”当成玩家当前格挡。新增 `player` 本地视觉模式，裁剪玩家区域并排除底部能量球，分别读取 `hp`、`max_hp`、`block`。数值只接受有界整数；未知保持 null，不能默认为 0，不能把分数文本转换为格挡。角色收到的玩家摘要由这些字段生成，不再沿用战场观察器的自由文本数值。字段校验仍不能保证模型每次都读对，实际效果继续通过后续画面核对。
- scene 模式在 battle/map 分类时明确返回空 targets，避免重复枚举将由专门模式读取的内容；奖励等交互场景仍保留具名目标。没有减少出牌前的牌面、能量或当前帧校验。
- 遮挡回放和实时测试还出现过 hp=1、max_hp=null 的不完整生命读数。生命分数现在必须同时读清且自洽，否则两项都保留未知，不能把缺半边的读数当作 1 血事实。原始模型输出仍保留以供对照。
- 停止入口仍直接调用执行器，统一任务同时收到取消请求；任务释放资源之前仍保持互斥。

## Windows 运行时诊断

本机 PATH 指向 Node 24.15.0，主服务曾无 JavaScript 异常日志退出；持有进程句柄的诊断记录捕获退出码 `-1073740791`（`0xC0000409`）。Node 官方仓库 [#63620](https://github.com/nodejs/node/issues/63620) 记录了同版本在 Windows HTTP 连接场景的相似原生退出，并报告较新版本不再复现。这是相近线索，本机没有崩溃转储，尚不能认定是相同内部原因。

本机已有可信 Node 24.19.0，现使用该版本继续运行，并将相同可执行文件保存在被忽略的 `runtime/node/node.exe`。没有改系统 PATH 或覆盖全局 Node，二进制不提交 Git。后续启动选择规则：

- Python 与 Windows PowerShell 主服务启动器：`AI_VTUBER_NODE` 指定的可执行文件 → 项目 `runtime/node/node.exe` → PATH。
- WSL `win-node`：`WSL_WINDOWS_NODE` → `AI_VTUBER_NODE` → 项目 `runtime/node/node.exe` → PATH。
- 显式覆盖值应使用可执行文件完整路径。Python 启动器在停止旧服务前验证新 Node 可运行，并在就绪回执报告实际版本。

此处只改变运行时选择，未屏蔽前台、输入停止或资源互斥校验。版本切换后的长时间稳定性继续随实机任务观察。

## 验证命令

视觉 worker 支持 `--model-dir` 或 `AI_VTUBER_VISION_MODEL_DIR` 选择已下载的本地 Qwen3-VL 检查点，默认仍为 4B。重启入口先检查架构配置、权重索引和全部分片存在，再停止当前项目的旧 worker；缺失检查点的实测请求被拒绝，原监听 PID 保持不变。PowerShell 入口复用相同检查，不再匹配并终止其他目录下的视觉进程。

官方 [Qwen3-VL-8B-Instruct](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct) 被选作离线对照候选，固定 revision `0c351dd01ed87e9c1b53cbc748cba10e6187ff3b`。权重保存在被忽略的 runtime 目录，尚不能仅凭模型更大宣称效果更好。对照请求使用已有截图和同一套本地 API，不包含游戏输入。

该权重已完整下载（17,534,339,512 字节），并以 NF4 实际载入本机 RTX 5080。4B/8B 同一组七项 API 回放报告分别为 `model-replay-Qwen3-VL-4B-Instruct-1793393919166.json`、`model-replay-Qwen3-VL-8B-Instruct-1793393995592.json`，保存在 `runtime/game-input/learning/`。两者在地图候选、已读清卡牌和奖励列表上接近；模型处理耗时合计分别约 23.87、24.59 秒。遮挡样本中，4B 返回不完整生命值并被归一化为未知，8B 则生成 1/1，与相邻未发生伤害输入的 75/80 读数冲突。这不是独立人工标注的准确率测试，但不足以支持升级实时模型；本次恢复使用 4B，8B 留作离线候选。结构自洽仍可能包含识别错误，不能只凭字段合法宣称感知正确。
