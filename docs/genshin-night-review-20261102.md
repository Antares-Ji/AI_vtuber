## 已落地的行为

- 跟标：转向后标记连续三次基本不变即返回；前进后距离增加超过 2m，或两次读数不下降即返回；仍保留缺标两帧、多目标拒绝和总轮次上限。没有距离时只能执行原有有界移动，不能声称得到距离进展验证。
- 重试：同一剧情分段累计两轮无效跟标后，校验器和原生执行器都阻止继续调用；wait、单独转镜不清零。有移动回执或传送调用返回才可重新尝试，这些回执仍不证明位移或到达。
- 交互停步：跟标、距离反馈移动、普通短移和区域探索都复核当前 OCR；F 提示（含歧义）、对话或菜单出现即返回模型。短移每段至多 400ms，跟标前进每段至多 500ms；释放后采集，不自动按 F。跟标因交互/对话退出时，不额外点击中键。
- F：模型选择 F 后，校验器绑定当前唯一目标文字；原生执行前重新识别。目标消失、变化或歧义则不按；同目标两次按后提示未变，停止盲重试。取消或异常时释放 F。
- 结果区分：回执记录 `sent`、`prompt_unchanged`、`scene_changed`、`prompt_changed_or_missing`；全部保留 `verified:false`。提示消失可能是遮挡、移动或 UI 延迟，不作为完成证明。
- 阶段记忆：长度至少六字的前缀截短视作兼容阶段，短到不足四字的读数不改变阶段；不同阶段需连续两次可用相同读数才清空已尝试锚点。恢复历史时兼容前缀读数，避免丢掉传送尝试。

`scripts/genshin/story-main.js` 中的纯 OCR 规则同时供 Node 校验器和 BetterGI 执行器使用，避免两侧标准漂移。Node 导入不会执行游戏会话。`src/genshin/story-runtime.js` 将交互证据、原生进展回执和新规则交给模型；`src/genshin/story-memory.js` 处理阶段防抖。

## 随后恢复试跑的经验

后续用户充值并重新确认 Windows 正常提权后，已开始真实试跑；以上“没有新增实机动作”仅指原夜间回顾的那一轮。持续会话、实际回执和修复记录见 `docs/genshin-continuous-training-20261102.md`。

- 失败次数必须按任务和阶段跨段持久化；正常分段或维护重启不能清空限制。
- 新版任务菜单缺少旧的固定标题，必须结合 OCR 布局；详情与列表同名是定位区域问题，不代表存在多个同名任务。距离必须绑定列表行。
- “严寒＋复苏”阻塞提示被误识别为大世界时，轮换移动、转向和 ESC 同样没有进展。场景许可必须在观察、校验和原生执行前一致检查，单独提示模型不够。
- 加载页的标题和说明与对话布局相似；没有自动标识、回复选项或本地视觉对话证据时，不应仅凭两块底部文字把菜单改判为剧情对话。
- 恢复按钮点击后，至少等下一帧验证提示消失及返回世界；这次已观察到界面恢复，仍不能计作剧情阶段完成或 F 成功。
- 当前 HUD 的“前去查看详情”也是任务阶段，不能只匹配“前往”；任务页出现“停止追踪”说明该任务已经追踪，不能为了刷新而取消。历史选中任务与当前追踪证据分别保存。
- 地图总览与地点详情均可能被本地场景模型误判为 world。采用地图 OCR 的组合布局补正，并禁止世界移动/F；单独地名或“传送”文字不足以改判地图。
- 旧 ESC 回执只有发送记录，连续相同界面不能推断游戏收到按键。代码审查发现缺少动作前窗口焦点核验；应记录输入时的前台证据，失焦停止，而不是把反复发键计作恢复。此缺口尚不能证明历史 ESC 无响应的唯一原因。
