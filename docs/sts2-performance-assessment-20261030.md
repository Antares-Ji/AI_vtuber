# 尖塔 API 自主执行：耗时与模型容量评估

评估日期：2026-10-30（America/Creston）。日志内保留UTC时间。目标是解释为何实测约8小时仅确认两场战斗结束，并决定能改善整局推进的改动。当前没有自主通关证据。

## 结论

主要证据指向两类问题：监督开发过程反复中断运行；在线循环串行重复观察和悬停。视觉能力存在真实短板，但尚不能将其归因于4B参数量，也没有证据证明DeepSeek本身无法胜任。当前角色决策实际使用DeepSeek，GPT/Codex负责监督开发，不直接决定游戏动作。

## 视觉4B与8B：同帧、同当前提示、同NF4与OCR检查

六项实际困难样本对照，总调用耗时4B为42.010秒，8B为42.545秒。样本未经独立人工像素标注，下面是输出差异与OCR一致性，不能换算准确率或通关率。

| 样本 | 4B | 8B | 判断 |
| --- | --- | --- | --- |
| 三张手牌费用冲突 | 原始牌名两处错误，两个8费；OCR保留1个费用 | 原始名称更完整，仍把撕裂读成3费；OCR可保留2个费用 | 8B局部改善，仍会错 |
| 高体型敌人 | 读出69/84并通过OCR | 同样69/84，原始名称更具体 | 血量均可用；8B返回数字ID，现接口不接受 |
| 防御完整牌面 | 名称、类型、规则核对通过 | 牌名null，规则未完整通过 | 8B该样本退步 |
| 抽牌堆查看 | 原始误判为待选牌 | 同样误判；牌名较好 | 两者仍依赖OCR界面纠正 |
| 遮挡玩家生命 | 原始15/80、格挡5；OCR不支持，保持未知 | 同样 | 参数增大未解决遮挡/证据缺失 |
| 展开的彼岸咆哮与邻牌 | 独立核对保留3费 | 格式适配后也保留3费 | 可用信息接近 |

8B两次手牌返回顶层数组而非cards对象。为避免把格式问题冒充视觉能力问题，离线比较仅将数组包装为cards，使用与4B完全相同的OCR记录重新归一化；没有改名称、数字或坐标。即使排除格式差异，结果仍有改善也有退步。8B没有直接部署为游戏运行模型，评估后恢复4B。

4B/8B均使用NF4量化，本次没有隔离比较BF16与NF4，因此无法判断错误中有多少来自量化。也没有评估更大视觉模型，不能由这六例断言参数量永远无效。

## 调用参数与硬件

本机GPU为RTX5080、总显存16303MiB。4B运行时总显存约11718MiB；一次8B加载阶段约13838MiB，均包含桌面和其他应用。4B战场读取期间五次采样GPU利用率约29%—33%，SM约2947MHz，功耗约113—125W。不能由这些短采样直接认定CPU、量化核或显存带宽谁是瓶颈；未关闭用户其他应用。

本地Qwen使用Instruct模型，不是额外开启长思考的Thinking模型。生成上限为场景/战场/手牌800token、牌面等350token；实际六例生成27—271token，没有达到上限。因此简单把max_new_tokens调小不会消除已经发生的逐字生成成本，反而可能截断JSON。源截图为1342×675，裁剪、遮挡、文字位置归属与输出格式都可能造成错误；参数量只是其中一个因素。

## 为何Minecraft脚本能跑不代表这套尖塔流程已合理

导入MC架构把结构化观察、慢规划、连续Task快执行和服务端回执分开。尖塔本轮采用用户要求的纯视觉路径，每次悬停都重新走场景、敌人、手牌、玩家、牌面、能量等串行请求，之后才交给DeepSeek决定一个键鼠动作。输入内容和动作粒度不同，不能把这套流程的延迟直接归因于同一个规划模型能力不足。应迁移MC的任务连续性与明确状态管理，不引入隐藏游戏状态代替纯视觉。
