# 0-1 部署延迟优化

> 本文是历史基线。最新专项YOLO三干员闭环及独立录像验收见[2026-09-12报告](realtime-deployment-20260912.md)：首位可部署→落地0.75～0.98秒，地图出现→落地3.43～3.68秒；完整体验仍未达一秒。

本次先优化本机控制通道。旧的19.3秒里，点卡片约3秒、两次拖动合计约12.2秒，占近八成；绿色格定位、方向定位和落地状态的本地模型调用合计约2.9秒。增加模型训练轮数不会消除重复启动控制进程产生的时间。

## 已实现

- 新增常驻控制器 `scripts/arknights-native-worker.ps1`，监听本机17644，复用已获授权的管理员控制进程启动。只编译一次原生绑定；同一进程内读取窗口、执行输入、截图和返回结果。保留17643旧通道及原可靠时序。
- 快速档保留绝对鼠标移动、按下、实际窗口检查、mouse_event释放、左键释放状态检查。按下等待由650ms缩到150ms，移动由40段×25ms调整到16段×15ms；缩短终点和释放等待。异常时也在finally释放左键。
- 快速档省去拖动中间的两张调试截图，仍保留每次动作后的截图、方向框和部署数检查，以及独立计时录像。
- 调用前更新过期画面；模型推理后重新截图对齐绿色格，避免选人镜头变化后使用旧位置。
- 结算与0-1地图节点必须有参考图证据；不再只凭千问声称“行动结束”就启动下一轮。短暂过渡页面用新截图轮询，加载等待可达90秒，独立录像的战斗响应计时从战斗画面出现开始。
- `node scripts/local-deployment-trials.js --fast-control` 启用本轮路径；两轮有限执行，不把聊天往返放入动作循环。启动器会复用常驻服务，必要时通过已有管理员控制器启动固定工作进程。

千问3-VL-4B完整BF16与YOLO11n均仍在本机参与推理。当前YOLO仍是通用COCO权重；本次提速不代表游戏专项检测训练已经达标。参考对齐与页面检查属于传统图像处理。

## 再往一秒内优化的顺序

1. 图像参考检查改成常驻服务，缓存参考图、特征和字形，避免当前每次重启Python、重新读取图片的约一秒累计开销。
2. 为敌人、可部署格、干员卡片、方向框、已部署干员建立人工核验的游戏数据集，训练并验证YOLO；按不同对局划分训练与验证，避免同一段录像的相邻帧混入两边。通用COCO检测速度快并不代表能识别这些类别。
3. 已确认场景使用快速检测、跟踪和本地规则处理连续动作；千问负责新场景理解、路线判断与低置信度复核，异步更新策略，避免每个动作串行等待数次VLM。只处理最新帧，过期结果不执行。
4. 根据真实方向框和落地画面逐步缩短剩余拖动时序。每次缩短都重新录屏验证；鼠标释放、扣费和部署数变化的检查继续保留。

一秒以内仍是待验证目标，不能由单次推理或截图耗时推算已实现。最终以独立录像中“战斗画面出现→干员真正落地”衡量，同时记录成功率、失败原因、P50和P95；目前样本不足以声称稳定P95。
